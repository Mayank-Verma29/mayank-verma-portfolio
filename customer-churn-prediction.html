MACHINE LEARNING / CASE STUDY 03

Customer Churn Prediction.

Using customer profile, tenure, contract and billing information to explore churn patterns, engineer features and compare classification models that predict whether a customer may leave.

PythonPandasScikit-learnLogistic RegressionStreamlit

01 / PROJECT OVERVIEW

Understanding customer retention risk

This project uses a synthetic customer dataset with 100,000 records to study churn behaviour and build a binary classification model. The workflow includes exploratory data analysis, feature engineering, preprocessing, model training and evaluation.

02 / BUSINESS QUESTIONS

Questions explored

  • How is churn distributed in the dataset?
  • How do contract type, monthly charges and tenure relate to churn?
  • Can engineered customer features help classification?
  • How do Logistic Regression, Decision Tree and Random Forest compare?
  • Can a simple app accept customer details and return a prediction?

The original synthetic dataset contains CustomerID, Age, Gender, Tenure, MonthlyCharges, Contract, PaymentMethod, TotalCharges and Churn. The cleaned dataset adds AvgMonthlySpend, Tenure_Group, Is_a_Long_Contract and High_Charges, along with an exported index column. The churn labels are No (66,856) and Yes (33,144).

Dataset note: the supplied data is synthetic. Results demonstrate a machine-learning workflow and should not be presented as measured outcomes from a real telecom company.

05 / FEATURE ENGINEERING & MODELLING

Preparing data for prediction.

The notebook creates average monthly spend (TotalCharges divided by Tenure, replacing zero tenure with one), groups tenure into New (up to 12 months), Mid-term (13–36 months) and Long-term (over 36 months), flags non-month-to-month contracts, and marks monthly charges of at least 70 as high charges.

A train/test split uses 80% training data and 20% test data (random_state=42). Numeric fields are standardised with StandardScaler and categorical fields are encoded with OneHotEncoder(handle_unknown="ignore"), combined through ColumnTransformer and Pipeline.

06 / MODEL EVALUATION

Comparing three classifiers.

0.58Logistic Regression churn F1

Logistic Regression — test-set classification report

For the churn class (Yes): precision 0.67, recall 0.51 and F1-score 0.58, with 6,706 churn-labelled test records. For the non-churn class (No): precision 0.78, recall 0.87 and F1-score 0.82, with 13,294 records.

Logistic Regression achieved the highest accuracy among the three models in the notebook. Its churn recall of 0.51 means it identified around half of the churn-labelled test cases, so accuracy alone is not sufficient to judge business usefulness.

Metrics are copied from the executed notebook's 20,000-row test set. The notebook does not report ROC-AUC, so no ROC-AUC result is claimed here.

07 / STREAMLIT APP

From model to interactive prediction.

The supplied Streamlit app collects customer details such as age, tenure, monthly charges, total charges, average monthly spend, gender, contract, payment method and engineered customer flags. On clicking Predict, it passes the entered features to a saved model and displays whether the customer is likely to churn or stay.

Run requirement

The app loads a file named lr_model.pkl from its working directory. The notebook includes a step that saves the fitted Logistic Regression pipeline to this filename. Keep the generated model file beside the app script before running it.

08 / KEY TAKEAWAYS

What this project demonstrates.

  • Exploratory analysis can reveal how churn labels vary across contract types, tenure and monthly charges.
  • Feature engineering adds customer-level indicators that can be used in a predictive workflow.
  • Preprocessing numeric and categorical data in a single pipeline keeps transformations consistent between training and prediction.
  • Model evaluation should consider churn precision and recall, not accuracy alone, because missed churn cases can matter to retention teams.
  • Retention ideas suggested by the patterns — such as reviewing month-to-month plans, onboarding and pricing — should be validated with real customer data before implementation.
